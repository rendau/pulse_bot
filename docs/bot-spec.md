# pulse_bot — вводная

Читать первым делом перед любой работой над ботом. Здесь то, что уже решено с заказчиком
в сессии разработки pulse (2026-09-23), и что осталось решить. План первой версии согласован
2026-09-23 (раздел «Первая версия»).

## Что строим

Telegram-бот, с которым можно поговорить об инфраструктуре: «что с caravan?», «что с
кластером?», «почему упали платежи, что поменялось перед этим?». Бот сам фактов не
собирает — он спрашивает языковую модель (LLM), а модель за фактами ходит в **pulse**.

```
Telegram ⇄ pulse_bot ⇄ LLM-провайдер (агентный цикл с инструментами; в v1 — OpenAI)
                              ⇅
                        pulse (MCP-сервер)
                              ⇅
             Kubernetes, Prometheus, Loki, Alertmanager, GitHub, kusec, ruto
```

## Решения

- **Отдельный сервис, отдельная репа.** Не часть pulse: у pulse есть доступ к кластеру,
  бот принимает сообщения из интернета и хранит ключи Telegram и LLM. Взлом бота не
  должен давать доступа к кластеру — только к тому, что pulse и так отдаёт через MCP.
  Так же сказано в ТЗ pulse (`pulse/docs/infra-mcp-spec.md`, раздел 7.2).
- **Go, скелет из gotemplate** (cookiecutter). Имя с `_`, потому что шаблон не пропускает
  дефис. Из шаблона убираем gRPC, grpc-gateway, proto, swagger и Postgres с миграциями —
  так же сделано в pulse (там осталось только HTTP).
- **Бот — MCP-клиент pulse.** SDK тот же, что у pulse на стороне сервера:
  `github.com/modelcontextprotocol/go-sdk` (там есть и клиент). Инструменты pulse
  передаются в модель как tools, вызовы модели — проксируются в pulse.
- **LLM — через свою абстракцию провайдера, в v1 — OpenAI.** Агентный цикл (шаги, лимиты,
  вызовы pulse, метрики) живёт в нашем коде и не знает, какой провайдер под ним. Провайдер —
  адаптер за общим интерфейсом: запрос (системный промпт, сообщения, инструменты с
  JSON Schema) → ответ (текст и/или вызовы инструментов, токены). Выбор адаптера — по конфигу
  (`LLM_PROVIDER`). Первый адаптер — OpenAI (официальный SDK `github.com/openai/openai-go`,
  Responses API); следующие (Anthropic и др.) добавляются новым адаптером без правок цикла.
  Служебное состояние провайдера внутри одного разбора (reasoning и т.п.) адаптер хранит
  непрозрачно для цикла; в историю между вопросами идёт только текст, поэтому смена
  провайдера историю не ломает.
- **Модель v1 — `gpt-6-sol`, reasoning effort `medium`** (выбрано 2026-09-23 по прайсу и
  карточкам моделей OpenAI). Sol — средняя модель GPT-6, «для сложного кода и агентных
  сценариев»: $2 / $0.2 (cached) / $10 за 1M токенов, ≈$0.2 за разбор с 5–8 вызовами pulse.
  Альтернативы: `gpt-6-astra` (сильнее, в 5 раз дороже — избыточна для разбора на пару минут),
  `gpt-6-luna` (в 20 раз дешевле — кандидат на удешевление, когда будет с чем сравнить).
  Запросы > 272K входных токенов тарифицируются вдвое — наша политика истории держит нас
  далеко ниже. Модель и effort — в конфиге (`LLM_MODEL`, `LLM_REASONING_EFFORT`): сменить —
  правка в kusec, без кода.

## pulse — что уже есть

- MCP streamable HTTP: снаружи — через ruto (ingress убран), внутри кластера —
  сервис `pulse` в namespace `default`, путь `/mcp`. Авторизация — `Authorization: Bearer
  <MCP_AUTH_TOKEN>` (токен у пользователя, в kusec pulse).
- Все инструменты read-only. Ошибка источника не роняет ответ: частичный результат +
  поле `errors`. Ответ ≤ 100 KB.
- 13 инструментов: `ping`, `resolve_service`, `list_services`, `get_service_info`,
  `get_service_snapshot`, `query_metrics`, `query_logs`, `get_timeline`, `get_changes`,
  `get_dependencies`, `get_public_api`, `call_service_endpoint`, `get_cluster_health`.
- pulse отдаёт в MCP `instructions` порядок диагностики: `get_cluster_health`, если лежит
  многое; иначе `resolve_service` → `get_service_snapshot` → `get_timeline` («что
  изменилось»), при необходимости `query_logs` / `query_metrics` / `get_changes` /
  `get_service_info`; при ошибках источников — `ping`. Имена сервисов брать только из
  `resolve_service` / `list_services`. Эти instructions стоит включить в системный промпт.
- Схемы ответов инструментов pulse меняются по мере развития: не кэшировать список
  инструментов навсегда, перечитывать при старте (и по ошибке валидации схемы).

## Первая версия (согласовано)

1. **Telegram:** long polling (не нужен входящий ingress); webhook — потом, если нужно.
   Библиотека `github.com/go-telegram/bot` со своим `http.Client` (тюнинг по общему правилу).
2. **Доступ:** белый список Telegram user ID из конфига; чужим — вежливый отказ, без ответа
   по сути. **Только личные сообщения**, в группах бот молчит (группы — потом).
3. **Разговор:** вопрос → агентный цикл LLM с инструментами pulse → ответ в чат.
   - История — в памяти, на чат: только вопросы и итоговые ответы, без промежуточных вызовов
     инструментов (ответ pulse до 100 KB — иначе каждый следующий вопрос дорожает).
     Последние ~10 пар, сброс после ~1 ч тишины, `/reset` — сброс сразу.
   - Один вопрос за раз на чат: пока идёт разбор, на новый — «ещё разбираюсь с предыдущим».
4. **Системный промпт** (из ТЗ pulse, 7.2): instructions pulse (порядок диагностики),
   формат ответа (коротко, по-русски, сначала вывод, потом факты), **не выдумывать значения**,
   явно говорить, какие источники недоступны (поле `errors`).
5. **Ограничители:** до 20 вызовов инструментов и 5 минут на ответ; по исчерпании — ответ
   тем, что успел выяснить, с явной пометкой, что разбор не закончен. Пока идёт разбор —
   «печатает…».
6. **Формат:** модель пишет обычный Markdown, бот конвертирует в Telegram HTML
   (`b`/`i`/`code`/`pre`/`a`); если Telegram не принял разметку — отправить plain text.
   Длинный ответ режется под лимит 4096 символов по абзацам, не разрывая блоки кода.
7. **MCP:** подключение при старте, список инструментов и `instructions` pulse — в модель.
   Перечитывать список при ошибке схемы и при переподключении.
8. **Метрики и логи** как у остальных сервисов (из шаблона): вопросы по исходу
   (ответ / отказ / ошибка), время ответа, шаги цикла, вызовы pulse по инструментам и их
   ошибки, ошибки LLM, токены (input / output / cached). Системный HTTP (порт 3003):
   `/healthcheck`, `/metrics`.

Не входит в v1: webhook, группы, личность пользователя в pulse, проактивный режим,
потоковый вывод ответа кусками, хранение в БД.

## Потом

- **Личность пользователя в pulse** — обязательное требование ТЗ (7.2): иначе любой в
  чате видит логи и конфигурацию всех сервисов. Для v1 заменено белым списком; позже —
  передавать в pulse, кто спрашивает, и разграничивать доступ там.
- **Проактивный режим** (ТЗ 7.3): алерт из Alertmanager → тот же разбор → сообщение в чат
  команды-владельца. Главная ценность продукта: разбор готов к моменту, когда человек
  открыл ноутбук. Тогда же — вероятно, Postgres (история, журнал разборов).
- **Другие LLM-провайдеры** (Anthropic и др.) — новым адаптером.
- **Работа в группах** — по упоминанию бота или reply; белый список проверяется по тому,
  кто спрашивает, а не по чату.

## Окружение и деплой

- Кластер `yc-zeon`, чарт — в `~/projects/mechta/helm-zeon/charts/` (ArgoCD, GitOps:
  push в master = деплой). Образ `ghcr.io/mechta-market/pulse_bot:latest`, keel.
- Весь env сервиса — в kusec (app `pulse_bot`), у деплоймента своих env нет. Не заводить
  `LOG_LEVEL`, `DEBUG`, `HTTP_CORS` без причины.
- Ожидаемые переменные: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ALLOWED_USERS`, `LLM_PROVIDER`
  (`openai`), `LLM_MODEL` (`gpt-6-sol`), `LLM_REASONING_EFFORT` (`medium`), `OPENAI_API_KEY`,
  `OPENAI_BASE_URL` (необязательно),
  `PULSE_MCP_URL` (внутри кластера — `http://pulse.default/mcp`), `PULSE_MCP_TOKEN`.
- Пользователь просит объяснять простыми словами: сначала суть и «решается/нет», детали —
  потом и кратко.
