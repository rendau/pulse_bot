# pulse_bot — вводная

Читать первым делом перед любой работой над ботом. Здесь то, что уже решено с заказчиком
в сессии разработки pulse (2026-09-23), и что осталось решить.

## Что строим

Telegram-бот, с которым можно поговорить об инфраструктуре: «что с caravan?», «что с
кластером?», «почему упали платежи, что поменялось перед этим?». Бот сам фактов не
собирает — он спрашивает Claude, а Claude за фактами ходит в **pulse**.

```
Telegram ⇄ pulse_bot ⇄ Claude API (агентный цикл с инструментами)
                              ⇅
                        pulse (MCP-сервер)
                              ⇅
             Kubernetes, Prometheus, Loki, Alertmanager, GitHub, kusec, ruto
```

## Решения

- **Отдельный сервис, отдельная репа.** Не часть pulse: у pulse есть доступ к кластеру,
  бот принимает сообщения из интернета и хранит ключи Telegram и Claude. Взлом бота не
  должен давать доступа к кластеру — только к тому, что pulse и так отдаёт через MCP.
  Так же сказано в ТЗ pulse (`pulse/docs/infra-mcp-spec.md`, раздел 7.2).
- **Go, скелет из gotemplate** (cookiecutter). Имя с `_`, потому что шаблон не пропускает
  дефис. Всё лишнее из шаблона для бота (gRPC, grpc-gateway, proto, возможно Postgres)
  можно убрать — так же сделано в pulse (там осталось только HTTP).
- **Бот — MCP-клиент pulse.** SDK тот же, что у pulse на стороне сервера:
  `github.com/modelcontextprotocol/go-sdk` (там есть и клиент). Инструменты pulse
  передаются в Claude как tools, вызовы Claude — проксируются в pulse.
- **Ответы пишет Claude** через официальный Go SDK Anthropic. Модель и параметры — выбрать
  по скиллу `claude-api` (не по памяти).

## pulse — что уже есть

- MCP streamable HTTP: `https://pulse.zeon.mdev.kz/mcp` (снаружи), внутри кластера —
  сервис `pulse` в namespace `default`, путь `/mcp`. Авторизация — `Authorization: Bearer
  <MCP_AUTH_TOKEN>` (токен у пользователя, в kusec pulse).
- Все инструменты read-only. Ошибка источника не роняет ответ: частичный результат +
  поле `errors`. Ответ ≤ 100 KB.
- 13 инструментов: `ping`, `resolve_service`, `list_services`, `get_service_info`,
  `get_service_snapshot`, `query_metrics`, `query_logs`, `get_timeline`, `get_changes`,
  `get_dependencies`, `get_public_api`, `call_service_endpoint`, `get_cluster_health`.
- pulse отдаёт в MCP `instructions` порядок диагностики: `get_cluster_health`, если лежит
  многое; иначе `resolve_service` → `get_service_snapshot` → `get_timeline` («что
  изменилось»), при необходимости `query_logs` / `query_metrics` / `get_changes` /
  `get_service_info`; при ошибках источников — `ping`. Имена сервисов брать только из
  `resolve_service` / `list_services`. Эти instructions стоит включить в системный промпт.
- Схемы ответов инструментов pulse меняются по мере развития: не кэшировать список
  инструментов навсегда, перечитывать при старте (и по ошибке валидации схемы).

## Первая версия (предложение, согласовать)

1. Telegram: long polling (проще, не нужен входящий ingress); webhook — потом, если нужно.
2. Доступ: белый список Telegram user ID из конфига; чужим — вежливый отказ, без ответа
   по сути. Работа в личке и в группах (в группе — по упоминанию бота или reply).
3. Разговор: вопрос → агентный цикл Claude с инструментами pulse → ответ в чат.
   Короткая история диалога на чат (последние N сообщений, в памяти), `/reset` — сброс.
4. Системный промпт (из ТЗ pulse, 7.2): порядок диагностики, формат ответа (коротко,
   по-русски, сначала вывод, потом факты), **не выдумывать значения**, явно говорить,
   какие источники недоступны (поле `errors`).
5. Ограничители: лимит шагов агентного цикла и общий таймаут на ответ; пока идёт разбор —
   «печатает…» / промежуточное сообщение; длинный ответ — разбить под лимит Telegram
   (4096 символов), Markdown экранировать.
6. Метрики и логи как у остальных сервисов (из шаблона): число вопросов, время ответа,
   ошибки Claude/pulse, токены.

## Потом

- **Личность пользователя в pulse** — обязательное требование ТЗ (7.2): иначе любой в
  чате видит логи и конфигурацию всех сервисов. Для v1 заменено белым списком; позже —
  передавать в pulse, кто спрашивает, и разграничивать доступ там.
- **Проактивный режим** (ТЗ 7.3): алерт из Alertmanager → тот же разбор → сообщение в чат
  команды-владельца. Главная ценность продукта: разбор готов к моменту, когда человек
  открыл ноутбук.

## Окружение и деплой

- Кластер `yc-zeon`, чарт — в `~/projects/mechta/helm-zeon/charts/` (ArgoCD, GitOps:
  push в master = деплой). Образ `ghcr.io/mechta-market/pulse_bot:latest`, keel.
- Весь env сервиса — в kusec (app `pulse_bot`), у деплоймента своих env нет. Не заводить
  `LOG_LEVEL`, `DEBUG`, `HTTP_CORS` без причины.
- Ожидаемые переменные: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ALLOWED_USERS`, `ANTHROPIC_API_KEY`,
  `PULSE_MCP_URL` (внутри кластера — `http://pulse.default/mcp`), `PULSE_MCP_TOKEN`.
- Пользователь просит объяснять простыми словами: сначала суть и «решается/нет», детали —
  потом и кратко.
